## 判定

整理すべき検証はある。ただし、見つかった主な問題は「コンパイラが保証済みのことを
大量に実行時確認している」ことではなく、移行用検証の残存、同じ実装への重複シナリオ、
バックエンドの業務判断と SQL の結合、テスト同士の前提データ共有である。

フロントは既に I/O port を差し替えられる。E2E でしか検証できない構造ではない。
バックエンドには改善余地があり、弱い内部型を強める前に異常系テストを削るのは順序が逆。

## 具体的な所見

### 1. 旧 HTTP adapter だけを試す5件は通常 CI から外す候補

[`tests/http-client.test.mjs:5`](https://github.com/Hosi121/SpeakUp-moonbit/blob/078cdecacdaed8a6896884e70f38bc90f7ab9641/tests/http-client.test.mjs#L5) は現行アプリではなく
`contract/frontend/httpClient.ts` と `errorUtils.ts` を import する。
[`contract/frontend/README.md:9`](https://github.com/Hosi121/SpeakUp-moonbit/blob/078cdecacdaed8a6896884e70f38bc90f7ab9641/contract/frontend/README.md#L9) も凍結した比較元と明記する。

旧 adapter 自体の試験は現在の adapter の回帰を直接検出しない。移行資料として残す価値と、
毎回の必須検証にする価値を分ける。旧側だけにあるエラー表示等のケースは現行側の
projection / decoder 試験で網羅を対応付け、足りないものだけ現行契約へ移す。
一方、旧 fixture と現行 MoonBit の結果を比較する parity 試験は現行実装を検査しており、別扱い。

`npm run fixtures` による凍結 Go / TS の再実行も、source / fixture / generator / toolchain の
変更時の検査へ限定する候補。通常はチェックイン済み fixture と現行実装の比較を続ける。
[`scripts/capture.mjs:43`](https://github.com/Hosi121/SpeakUp-moonbit/blob/078cdecacdaed8a6896884e70f38bc90f7ab9641/scripts/capture.mjs#L43) の Go 実行はこの再生成のためである。

### 3. 同一 CI 内の単純な二重実行も残る

[`scripts/test-boundaries.mjs:7`](https://github.com/Hosi121/SpeakUp-moonbit/blob/078cdecacdaed8a6896884e70f38bc90f7ab9641/scripts/test-boundaries.mjs#L7) は `core/wire` の JS 2件を

### 5. バックエンドは業務判断・SQL・通知が同じ関数にある

[`core/api/runtime.mbt:13`](https://github.com/Hosi121/SpeakUp-moonbit/blob/078cdecacdaed8a6896884e70f38bc90f7ab9641/core/api/runtime.mbt#L13) の `Host` は `async (Json) -> Json`、

形を知った fake を作りやすく、業務上の契約を型で示せていない。

具体的には [`core/api/social.mbt:43`](https://github.com/Hosi121/SpeakUp-moonbit/blob/078cdecacdaed8a6896884e70f38bc90f7ab9641/core/api/social.mbt#L43) の `friendship` が

実 DB＋HTTP 経由で検証され、対応する独立した業務ルール試験は見つからなかった。

型付きの友情状態・操作・actor から次の状態/拒否を決める関数を切り出すのが先。
repository adapter に transaction・ロック・一意制約・競合時の再読込を残す。
DB の原子性を fake repository の試験で代用したり、ロック外の事前判定だけに移してはならない。
SQL 文字列そのものを期待値にした mock を増やす方法は、結合をテストへ移すだけになる。

## 型で置き換えられる検査と、残す検査

| 対象 | 判断 |
| --- | --- |
| 内部 record の field 型・enum の選択肢 | コンパイラに任せる。型が既に保証する内容のためだけに実行時テストを追加しない |
| JSON / DB / JS FFI の入力 | 型の外から来るため decoder 試験を残す。整数の小数・桁あふれ・欠落を消さない |
| 生成 `.d.ts` と実 JS の整合 | 自作生成器も検証対象。独立 consumer の型検査と、代表的な runtime ABI 試験を残す |
| 認可・時刻・再試行・古い callback の拒否 | 引数の型だけでは処理順序と結果を保証しない。小さな単体試験を残す |
| SQL 原子性・実 socket 切断・WebRTC RTP・DOM focus/IME | 実 DB / socket / browser の検証が必要。責務ごとに最小の実環境で確認する |

[`tests/http-contracts.test.mjs:6`](https://github.com/Hosi121/SpeakUp-moonbit/blob/078cdecacdaed8a6896884e70f38bc90f7ab9641/tests/http-contracts.test.mjs#L6) 等は不正な JSON を
decoder に渡す検証で、型検査の繰り返しではない。
[`tests/js-boundary-consumer.mts:5`](https://github.com/Hosi121/SpeakUp-moonbit/blob/078cdecacdaed8a6896884e70f38bc90f7ab9641/tests/js-boundary-consumer.mts#L5) は既に
`@ts-expect-error` で生成型の拒否をコンパイル時に確認している。

型をさらに活かせる箇所はある。通話内部の `Phase` は enum だが、公開操作は
[`Snapshot`](https://github.com/Hosi121/SpeakUp-moonbit/blob/078cdecacdaed8a6896884e70f38bc90f7ab9641/core/conversation/model.mbt#L3) の時刻3個＋revision を毎回 `restore` する。
検証済みの opaque な Conversation を内部 API に渡し、wire/storage Snapshot の decode は境界に
寄せられる。`ParsedSignal.kind : String` やフレンド `action : String` も内部では enum の候補。
ただし enum にしただけで正しい遷移・参加権限まで証明されるわけではない。

## 推奨する変更単位

| 順序 | 変更 | 対象 | 期待する検証への影響・完了条件 |
| --- | --- | --- | --- |
| 1 | 移行用検証と二重実行の整理 | 旧 HTTP 試験、boundary script、fixture 生成と workflow | 旧 HTTP 5件を通常 CI から外す候補。wire JS2件＋JS境界3件の再実行を除く。現行契約を失わない対応表を作る |
| 2 | 同一 message renderer の検証を一か所へ集約し、browser 試験の DB 依存を外す | navigation/message、browser/http、Playwright config | 重複6シナリオを整理。単独 host の寿命確認、実 DOM/IME、安全な文字表示、実 RTP は残す。HTTP5ケースは件数を維持して DB 不要へ |
| 3 | API 試験の fixture をケースごとに独立 | features.test.mjs | メッセージ試験等が単独・順序変更でも同じ結果になる。必要な共有サーバ起動まで毎回重複させない |
| 4 | フレンド状態遷移を型付き domain と repository 境界へ分ける | core/api/social、runtime、新しい domain、API/DB試験 | 拒否・再申請等の組合せを DB なしで試す。実 transaction / 同時承認 / 通知一意性と API 認可接続は実 DB で維持 |
| 5 | 通話・signal の検証済み内部型を強める | core/conversation、shared/protocol、各 adapter | 不正状態を作れる範囲を境界へ限定。内部重複検査の削減は型変更後。JSON契約・相互運用性・遷移の意味は維持 |

coverage の増減率は未計測なので数値を付けない。重複を減らす件数と、独立して検出できる
不具合の種類を減らさないことを分けて確認する。前回の135件は短時間であり、整理だけで
CI が大幅に短縮するとは主張しない。主な価値は、変更に追従しやすく原因を特定しやすい検証へ直すこと。

## Router / controller の残すべき branch 確認

- route の同一性・alias・query 変更・遅延 chunk の世代判定: controller 単体を中心にし、
  browser back/forward・修飾クリック・直 reload の配線をブラウザで残す。
- request の成功/HTTP失敗/不正body/停止後の完了: controller / decoder / transport の各責務へ。
  一つの異常入力を全画面・全 backend で繰り返さない。
- message の送信中・再試行・既読・古い応答: controller で網羅し、DOM のイベント配線・focus・
  composing input 保持をブラウザで確認する。
- invitation → RTP → 切断/再接続 → 終了/振り返り: 代表 E2E を残す。enum のみでは証明できない。

変更時に失敗したテストは、期待する仕様の変更・実装バグ・テスト自体の誤りを分けて判断する。
単に現在の実装へ expected を書き換えない。外部の振る舞いを変える判断が必要な場合だけ、
何が変わるかを明示してユーザーに判断を求める。
